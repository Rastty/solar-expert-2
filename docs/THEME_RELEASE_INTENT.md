# Solar Expert: explicit theme release intent

The `dev` branch is an integration lane, **not** an implicit permission to
replace the live WordPress theme or synchronize managed content on each merge.

## Default behavior

`.github/workflows/auto-deploy-dev.yml` still runs on every `dev` push.
Its **release-intent** job verifies exactly what changed between the pushed
commit and its predecessor. Unless `ops/theme-deploy-release.json` changed
on **that specific push** and is validly enabled, the entire `deploy` job is
skipped. Regular merges, theme code changes, test-only changes, retries, and
disarming do **not** touch production.

The release control on `dev` starts disabled:

```json
{
  "schema_version": 1,
  "enabled": false,
  "mode": "explicit_theme_release",
  "release_id": ""
}
```

The actual version in the repository has additional explanatory fields.

## Only when a complete theme release is proven safe

Create a reviewed **separate** branch/PR targeting `dev` which makes a
deliberate change to `ops/theme-deploy-release.json` with `enabled:true`
and a unique, auditable `release_id` formatted like
`solar-theme-verified-20261108a`. Do not edit this file as part of normal
feature or editorial merges.

Before merging, the release owner still needs reliable proof of the host
database and uploads restoration path, exact release scope, current-head
`Validate Solar Expert` and `WordPress Playground Preview` successes,
and an acceptable rollback procedure. The deployment's existing checks
also verify the merged dev commit, exact preview PR, production version,
managed content, category/indexability state, public tool behavior and
retailer attribution. No editorial approval implies authority to change
these distinct safeguards.

Upon a qualifying `dev` merge, only its **first push** activates this
job; the existing validation/preview/release checks remain in force.
The release ID is an audit trail, not an API token or secret. The developer
should return the control to `enabled:false` on a separate PR after a
successful verified release. This disarm push will not redeploy. A later
ordinary merge will also not redeploy even while the control remains true,
because the control file itself was unchanged.

## Additional mandatory pre-production evidence

Even a reviewed one-time `enabled:true` theme release **cannot deploy**
without the separate private, release-scoped
`SOLAR_EXPERT_WORDPRESS_BACKUP_RECEIPT` in GitHub Actions. The receipt
requires genuine host DB and uploads backup references no older than
24 hours, a staging restore drill within 30 days, an actual accountable
owner, and the exact previous `dev` commit SHA. The receipt is a
**private attestation, not a database backup or independent proof of
restoration**; the host restore itself must be demonstrated first.
See [the release-specific restore requirements](WORDPRESS_RESTORE_ATTESTATION.md)
and [open recovery blocker #148](https://github.com/Rastty/solar-expert-2/issues/148).

After that, the release workflow compares four currently public theme
source files byte-for-byte with its first-parent rollback candidate,
stores a verified previous-theme code archive before mutation,
and rejects any stale `dev` ref or ambiguous Deployer/sync response.
`main` editorial publishing remains a separate narrowly authorized
single-post lane, not a theme-release override. Do not simply switch the
theme release control to true while the host backup/restore proof is
unverified.

**Important migration limitation:** `dev` may already contain several
reviewed improvements that are absent from the current public theme.
In that case live source SHA256 will intentionally differ from the
immediately previous `dev` commit and the new preflight will **block
the release**. A responsible release engineer must create and review a
real current-live rollback baseline or a separately proven migration
path. Never skip the public source-drift check to make a green run.

## Editor posts are separate

The main-branch native editorial publisher uses
`ops/editorial-release.json` with an exact source manifest and WordPress
Application Password. It is **not** a theme release and is not affected by
this `dev` workflow. Its rolling 24h post-creation limit and one-write
anti-replay remain unchanged. No theme release is required simply to
publish one authorized technical article through WordPress REST.

## Safety notes

- The release intent gate only creates a clear separation between
  integration and deployment. It is not itself a full pre-deploy host backup.
- On missing previous commit, malformed control, wrong release ID, or
  ordinary `dev` changes the gate fails closed (no production deploy).
- The concurrency group is non-cancelling so a new dev merge cannot
  interrupt an in-flight deployment. Future release operators should still
  inspect the existing run before starting a second production release.
- Never use `workflow_dispatch` or an ad-hoc URL as an unreviewed bypass of
  the change-controlled release. This workflow has only the `dev` push trigger.
- Offline tests in `tests/theme-deploy-release-gate.test.mjs` exercise the
  actual gate shell with real local Git history, including ordinary pushes,
  explicitly enabled control, stale enabled state, malformed ID and disarming.
